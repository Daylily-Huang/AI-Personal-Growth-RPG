# 总体结论：**CONDITIONAL PASS（有条件通过）**

这个初版不是“假的 Demo”，核心架构确实已经搭起来了，而且**Growth Engine、AI Proposal、Confirm→XP Ledger、Dashboard、Skill Tree 雏形**都是真代码。仓库结构也比较清晰。

但我**不建议马上无脑继续堆功能**。现在有一个和游戏底层规则直接冲突的问题，应该先修；另外 Confirm 的“幂等性”目前只证明了顺序调用安全，没有证明并发安全。

# 一、我确认做对了的地方

## 1. Growth Engine 的方向是正确的

`src/lib/growth-engine/xp.ts` 是真正独立的确定性模块。

它明确做到：

```text
相同 input
→ 相同 XP
```

不读取数据库、不调用 AI、不依赖当前时间。

这个架构非常重要，我赞成继续保持：

```text
AI
↓
给语义评分

Growth Engine
↓
根据固定规则算 XP
```

而不是：

```text
AI：我觉得你应该 +357 XP
```

### 时间规则也实现对了

目前：

```ts
1.00 → 1.15
```

时间最多只提供 15% 的修正，而且 180 分钟以后基本饱和。

所以：

```text
60 min
```

和

```text
300 min
```

绝不会因为时间本身变成 5 倍 XP。

这符合我们之前定的原则。

# 二、重复行为机制本身也写出来了

代码中：

```text
第一次        ×1.00
2–3 次        ×0.80
4–10 次       ×0.40
更高重复       ×0.15
```

同时：

```text
Novelty 越高
→ 可以解除部分重复惩罚
```

所以设计思想实际上不错。


XP 很低。

但：

```text

+
第一次真正搞懂 LC 推导
```

Novelty 高，就能减轻重复惩罚。

这个逻辑值得保留。

# 但并发情况存在风险

如果两个请求同时来：

```text
Request A        Request B

read pending     read pending
     ↓                ↓
calculate XP     calculate XP
     ↓                ↓
write            write
```

两边在读取时都有可能看到：

```text
status = pending
```

当前 JSON store 没有：

```text
DB transaction
unique constraint
mutex
row lock
```

因此我不会接受：

> “Confirm 已完整保证幂等。”

更准确应该是：

> **单线程/顺序场景幂等已实现；并发幂等未保证。**

# 为什么 Supabase 后这个问题比较好解决？

数据库里可以直接设置：

```sql
unique (assessment_id)
```

例如：

```text
xp_transactions.assessment_id UNIQUE
```

即使两个请求同时进来：

```text
A → INSERT 成功
B → UNIQUE constraint failed
```

数据库会帮你守住。

这也是 Supabase/PostgreSQL 的真正价值之一。

> XP 评价是客观的。
