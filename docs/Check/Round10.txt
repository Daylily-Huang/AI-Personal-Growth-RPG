# 四、新发现：`pg` 很可能还缺 `@types/pg`

这个是 Round9 里我认为最值得补的一点。

现在 `package.json` 已经有：

```json
"pg": "^8.13.0"
```



但仓库里没有：

```text
@types/pg
```

而 smoke test 又写了：

```ts
let Client: typeof import("pg").Client;
```



你的 `tsconfig.json`：

```json
"strict": true
```

而且 include 是：

```text
**/*.ts
**/*.tsx
```

所以测试代码也包含在 TypeScript 工程范围内。

这里有一个现实风险：

> `pg` 8.x 本身目前不是一个内置完整 TypeScript declarations 的包。

node-postgres 官方当前 package manifest 没有暴露 bundled `types`，而维护者在 2026 年讨论 pg 9 时还专门把“bundle TS type definitions”列为未来工作。

所以我高度建议直接补：

```bash
pnpm add -D @types/pg
```

也就是：

```json
"devDependencies": {
  "pg": "^8.13.0",
  "@types/pg": "..."
}
```

否则真实执行：

```text
pnpm build
```

或单独：

```text
tsc --noEmit
```

时，很可能遇到：

```text
Could not find a declaration file for module 'pg'
```

我把它定为：

## **P1，但很好修。**

# 六、`0019` 当前设计还有两个小问题，但不再阻塞 Stage2

一个是 constraint existence 检查现在主要按：

```sql
where conname = 'xxx'
```

判断。

长期更严谨可以加：

```text

conrelid
```

避免别的 schema/table 恰好有同名 constraint。

例如：

```sql
where conname = 'fk_xp_transactions_skill'
and conrelid = 'public.xp_transactions'::regclass
```

但对于你当前这个单项目 migration，这属于 **P2**。

另一个是 smoke test 要求：

```text
FRESH database
```

但测试本身不会自动：

```text
drop schema
reset project
```

所以 CI 最终应该给它一个专用 disposable database，或者使用本地 Supabase `db reset`，而不是对长期开发库反复跑完整 migration。

同样不阻塞当前代码。

# 八、我现在真正关心的是 Stage2 的 `SECURITY DEFINER`

你们已经选定：

```text
普通 authenticated client
→ 永久成长态只读

settle_activity()
→ SECURITY DEFINER
→ 权威写入
```

这个架构方向是正确的。

但 Stage2 写 RPC 时，安全要求要非常严格。

PostgreSQL 官方明确说明：`SECURITY DEFINER` 函数以函数 owner 的权限执行，因此必须特别防止被滥用，并建议把 `search_path` 限制到可信 schema，避免可写 schema/临时对象劫持。

所以 Stage2 的 RPC 不能只是：

```sql
security definer
```

然后结束。

至少应该类似：

```sql
security definer
set search_path = public, pg_temp
```

并且：

```text
不要接受 user_id 作为可信参数
```

而应该：

```sql
v_user_id := auth.uid();
```

然后从：

```text
assessment
→ activity
→ current user
```

内部推导 Skill、repetition、transaction ownership。

# 九、RLS 的理解现在比 Round7 正确很多

这是 hy3 两轮里我认为最明显的质量提升。

Round7 的方案，本质上理解 RLS 为：

```text
User A 只能操作 User A 的 row
```

所以所有表都：

```text
SELECT
INSERT
UPDATE
DELETE
```

只要：

```sql
user_id = auth.uid()
```

即可。

而 Round8 改成：

```text
第一层：
这是不是你的数据？

第二层：
即使是你的数据，
你有没有权限直接修改这种状态？
```

这才是正确的 authority model。

PostgreSQL RLS 本身确实支持针对 SELECT / INSERT / UPDATE / DELETE 分别建立不同 policy；没有允许某项操作的 policy 时，会落到默认拒绝。

对于 Personal Growth RPG：

```text
我的 Activity
```

和：

```text
我的 XP Ledger
```

虽然都是“我的”，权限语义根本不一样。

这一点 hy3 这两轮处理得比最早版本成熟很多。
