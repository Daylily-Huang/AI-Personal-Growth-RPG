# 一、最重要的问题：Assessment 写入权限和 SupabaseRepository 自相矛盾

这是这轮最关键的问题。

当前 `SupabaseRepository.addAssessment()` 明确使用传入的用户 session client：

```ts
this.client
  .from("ai_assessments")
  .insert(...)
```

然后再：

```ts
this.client
  .from("activities")
  .update({ status: "assessed" })
```

而这个 client 来自：

```text
request cookie
→ getSupabaseServerClient()
→ auth.getUser()
→ SupabaseRepository(client, user.id)
```

也就是**普通 authenticated 用户 JWT + RLS**。这部分 request-scoped Auth wiring 本身是正确的。

问题是我们的 Round8 authority matrix 已经明确规定：

```sql
create policy ai_assessments_select
...
for select to authenticated
```

但**没有**

```text
ai_assessments_insert
```

policy。

也就是说真实 Supabase 下：

```text
POST Assess
↓
AI Proposal 生成成功
↓
SupabaseRepository.addAssessment()
↓
INSERT ai_assessments
↓
RLS DENY
```

所以目前这部分：

这说明 Stage2-A 的验证还主要停留在：


没有真正做：

# 四、具体怎么实现，我推荐这一种

可以新增一个很小的数据库函数，例如：

```text
record_ai_assessment
```

但它和之后的 `settle_activity` 有一个关键区别：

### 不给 authenticated 直接调用。

权限应该类似：

```sql
REVOKE EXECUTE
ON FUNCTION record_ai_assessment(...)
FROM PUBLIC;

REVOKE EXECUTE
ON FUNCTION record_ai_assessment(...)
FROM authenticated;

GRANT EXECUTE
ON FUNCTION record_ai_assessment(...)
TO service_role;
```

然后 Next.js 的 assess route：

```text
1. user-scoped client
   → auth.getUser()

2. user-scoped read
   → Activity 必须属于当前 user

3. AI 生成 Proposal

4. server-only admin client
   → record_ai_assessment(...)
```

RPC 内：

```text
验证 activity.user_id
=
传入的已认证 user ID

验证 Activity != confirmed

使用 Activity.rules_version
而不是 client 提供的版本

INSERT ai_assessment

UPDATE Activity
pending_assessment → assessed

同一个数据库 transaction
```

这样：

```text
Browser
```

永远没能力自己伪造 Assessment。

而：

```text
Next server
```

只有在它自己调用 AI 后才能完成这个写入。

这属于真正合理使用：

```text
SUPABASE_SECRET_KEY
```

的场景——**可信 server-generated state**。

不是“普通 CRUD 全用 secret”。

# 五、这还顺带解决了当前 addAssessment 的第二个问题：它不是原子的

同一个 transaction，
