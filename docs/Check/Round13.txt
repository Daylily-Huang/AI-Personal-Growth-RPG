# 一、这轮哪些东西是真的修好了

### 1. Assessment 已经不再由 authenticated client 直接 INSERT

这一点修复方向正确。

现在：

```ts
SupabaseRepository.addAssessment()
```

已经不再 `.from("ai_assessments").insert(...)`，而是明确抛错，要求走 server-only persistence。

并新增：

```text
AssessmentPersistenceService
        ↓
admin.rpc("record_ai_assessment")
        ↓
SECURITY DEFINER
```

RPC 内部：

* 锁 Activity；
* 检查 `activity_id + user_id`；
* 从 Activity 继承 `rules_version`；
* INSERT Assessment；
* Activity → `assessed`；
* 同一数据库事务完成。

SQL 本身这部分设计基本成立。

**原 Round12 P1-1：核心数据库问题基本解决。**


因此用户通过普通 UPDATE：

这条路径已经封掉。

# 二、P1-1：Activity 状态仍然可以从 **INSERT** 伪造

这是本轮最重要的新发现。

你们只关闭了：

> UPDATE status

但没有关闭：

> **INSERT 一个一开始就是 confirmed / assessed 的 Activity。**

0018 仍然保留：

```sql
create policy activities_insert on public.activities
  for insert to authenticated
  with check (user_id = auth.uid());
```

除此以外**没有任何字段约束**。

而 Activity 本身允许：

```sql
status in (
  'pending_assessment',
  'assessed',
  'confirmed'
)
```

所以恶意 authenticated client 目前理论上可以直接提交类似：

```text
user_id       = 自己
status        = confirmed
rules_version = 随便写
created_at    = 随便写
activity_type = 随便写
```

RLS 会认为：

> user_id 是你自己的，允许 INSERT。

更关键的是，0020 的 immutability trigger 是：

```sql
before update
```

**它根本不检查 INSERT。**

因此 Round12 摘要中的：

> “客户端不能伪造 assessed、confirmed”

严格来说仍然不成立。

### 为什么这是 P1

它目前不能直接给自己铸造 XP，所以我不判 P0。

但是它能制造：

```text
confirmed Activity
+
没有 Assessment
+
没有 XP ledger
```

这种系统状态。

而且 `rules_version` 本来应该是 authority-controlled 的审计事实，现在客户端同样可以自行决定。

这直接破坏：

> Activity lifecycle authority invariant

### 推荐修法

不要继续往 `activities_insert` 上打补丁。

更干净的方法是：

```text
authenticated client
        ↓
create_activity RPC
        ↓
数据库自己决定
user_id       = auth.uid()
status        = pending_assessment
rules_version = authoritative current version
created_at    = now()
updated_at    = now()
```

然后：

```sql
DROP activities_insert
```

客户端只提交真正属于用户事实的数据，例如：

```text
raw_input
total_minutes
effective_minutes
quest_id
```

**status / rules_version / audit timestamp 不让客户端提交。**

这才符合这个项目此前一直强调的：

> client is hostile / server owns permanent state.

# 三、P1-2：`database.types.ts` 仍然是“过期 generated types”

这个问题很明确。

Round12 摘要声称 generated types 已经覆盖：

> RPC `record_ai_assessment`



但我查看当前 `main` 的：

```text
src/lib/supabase/database.types.ts
```

实际是：

```ts
public: {
  ...
  Functions: {
    [_ in never]: never
  }
}
```

也就是说：

## `record_ai_assessment` 根本不存在于当前提交的 generated types 中。

而 SQL 中它显然已经存在。

因此现在形成了：

```text
Migration schema
    ≠
database.types.ts
```

这正是上一轮我们要消灭的 schema drift。

### 为什么 TypeScript 还能通过？

因为：

```ts
getSupabaseAdminClient()
```

创建客户端时写的是：

```ts
createClient(url, secretKey, ...)
```

没有：

```ts
createClient<Database>(...)
```

所以这一句：

```ts
admin.rpc("record_ai_assessment", ...)
```

没有真正受到 `Database` 类型系统约束。

换句话说：

> **TypeScript 通过反而暴露出了 generated types 没真正接进 admin RPC。**

browser/server factory 同样没有把 `Database` generic 接进去。

### 应该怎么修

0021 migration 完成后重新：

```bash
pnpm db:types
```

然后必须看到：

```ts
Functions: {
  record_ai_assessment: {
    Args: {...}
    Returns: ...
  }
}
```

随后三个 factory 全部改为 typed：

```ts
createClient<Database>(...)
createServerClient<Database>(...)
createBrowserClient<Database>(...)
```

这样如果以后：

```sql
record_ai_assessment(...)
```

改参数而忘了 regenerate types，`tsc` 就应该直接炸掉。

这才叫 schema type safety。

# 四、P1-3：Assessment persistence 已经造出来了，但**没有真正 wiring**

这是架构层的问题。

现在 `Repository` interface 明确要求：

```ts

```

但是 Supabase implementation 是：

```ts
async addAssessment(...) {
  throw new Error(
    "Use AssessmentPersistenceService..."
  );
}
```

与此同时，新建的：

```text
AssessmentPersistenceService
```

目前搜索整个仓库，**没有实际业务调用者**。

现有 `/assess` route 还是：

```ts
const repo = getRepository();
...
const assessment = await repo.addAssessment(...)
```

而且用的还是 DemoRepository。

`getAuthenticatedRepository()` 目前同样没有进入实际 route。

所以当前真实情况是：

```text
Demo route
    ↓
Repository.addAssessment()
    ↓
正常

SupabaseRepository
    ↓
Repository.addAssessment()
    ↓
直接 throw
```

因此如果现在单纯把：

```ts
getRepository()
```

换成：

```ts
getAuthenticatedRepository()
```

Assessment route 会直接 500。

## 这不是 Supabase “wiring closure”

目前更准确的说法应该是：

> **Supabase authority primitives prepared**

而不是：

> authority wiring closed.

### 推荐架构

现在正好应该拆 port。

不要再让一个巨大的 `Repository` 同时承担：

```text
user reads
user-authored writes
AI trusted writes
settlement trusted writes
```

可以逐渐拆成：

```text
ActivityRepository
AssessmentReader
AssessmentWriter        ← server only
SettlementWriter        ← server only
GrowthStateReader
```

然后 assess route：

```text
1. authenticate
2. RLS ActivityRepository.getActivity()
3. AI assess
4. AssessmentWriter.record(...)
5. return Assessment
```

这样 authority boundary 会非常清楚。
