# P1-2：新的核心并发 DB 测试本身写错了

新测试的目标非常正确：

> 两个不同 Activity，同一 Skill，同时 Settlement。

这正是上一轮要求补的最重要并发测试。

但它的 conflict retry 对象写反了。

当前代码：

```ts
const conflictIdx = results.findIndex((r) => !r.ok);

const conflictAct =
  conflictIdx === 0 ? act2 : act1;
```



这是反的。

如果：

```text
r1 / act1 = repetition_conflict
```

那么：

```text
conflictIdx = 0
```

应该 retry：

```text
act1
```

现在却 retry：

```text
act2
```

而 act2 恰好是刚刚成功结算的那个 Activity。

因此 retry 很可能得到：

```text
already_confirmed
```

而不是：

```text
ok=true
```

正确代码应该是：

```ts
const conflictAct =
  conflictIdx === 0 ? act1 : act2;
```

而且更好的是不要硬编码：

```ts
repetitionCount: 1
```

应该读取：

```text
actualRepetitionCount
```

然后用数据库返回的 authoritative value retry。

### 为什么这个 bug 很关键

当前两个 settlement 一开始都提交：

```text
repetitionCount = 0
```

如果数据库的同 Skill serialization 正常：

```text
第一个 → success, count=0
第二个 → repetition_conflict, actual=1
```

所以这个 conflict branch **本来就应该被走到**。

也就是说它不是一个“偶尔触发”的测试 bug。

它基本正好位于这个测试正常执行的主路径上。

因此目前 Summary 写的：

> cross-activity same-skill 并发已覆盖

更准确应该写：

> **测试已经编写，但尚未通过真实 DB 执行，而且当前静态审查发现 retry target bug。**

这也是 **P1 verification gate**。

# P2-1：所谓“repetition conflict 零副作用”仍然不完全成立

Summary 写：

> 所有验证先于所有永久写入。

这句话严格来说仍然不成立。

因为 Phase C 已经执行：

```sql
insert into public.skills (...)
on conflict (...) do nothing
returning id ...
```

而 repetition check 是 Phase F。

对于**已经存在的 Skill**，`DO NOTHING` 确实不会再修改它。

因此现有 P2-A test：

```text
已有 SideEffect Skill
→ 记录 xp/updated_at
→ repetition_conflict
→ 检查 xp/updated_at 不变
```

是可以通过的。

但是如果 Skill **原来不存在**：

```text
Skill 不存在
↓
Phase C INSERT Skill
↓
Phase F repetition_conflict
↓
RETURN {ok:false}
```

由于这是正常 `RETURN`，不是 exception rollback：

```text
新建 Skill 仍然会提交
```

于是：

```text
Confirm 失败
但数据库多出一个 Skill
```

所以“零副作用”只对 existing Skill 成立。

### 推荐修法

最干净的是对：

```text
user_id + normalized skill name
```

先做 transaction-level advisory lock。

然后：

```text
lock normalized skill key
↓
SELECT existing skill
↓
如果不存在：
authoritative repetition = 0
↓
先验证 repetition
↓
全部验证通过
↓
才 INSERT Skill
```

这样才是真的：

> no permanent write before validation.

我暂时仍判 **P2**，因为它不会错误加 XP，但语义没有完全达到声明。

# P2-4：`request_verification` 仍没有做 stale mastery 校验

目前 Phase G 只处理：

```text
masteryAction = upgrade
```



没有处理：

```text
request_verification
```

所以理论上：

```text
SettlementService 读 M1
→ 决定 request M1→M5

等待期间
另一 settlement 已把 skill 升到 M5

旧 settlement 获得锁
→ 仍创建 pending M1→M5
```

于是数据库出现一个实际上已经没有意义的 verification。

更合理的是锁后：

```text
if toLevel <= currentMastery:
    verification = none
```

如果：

```text
currentMastery > fromLevel
但 < toLevel
```

则至少应把 authoritative：

```text
fromLevel = currentMastery
```

而不是保留 stale `fromLevel`。

这不会马上导致 Mastery 降级，所以我判 P2。
