# P1-1：新 Skill 的 Mastery DB 不变量仍有一个 NULL 漏洞

这是本轮唯一新发现的核心代码问题。

Skills 表明确规定新 Skill：

```sql
mastery_level integer not null default 1
```



`SettlementService` 同样明确：

```ts
const DEFAULT_SKILL_MASTERY = 1;
```

也就是说，系统定义很清楚：

> **新 Skill 当前 Mastery = M1。**



但 0026 的执行顺序现在是：

```text
Phase C
查 Skill

不存在：
v_skill_is_new = true
v_skill_row 没有真实 row
        ↓
Phase G
检查 Mastery
        ↓
Phase H
才真正 INSERT Skill（默认 M1）
```



于是 Phase G 写的是：

```sql
if v_proposed_level <= v_skill_row.mastery_level then
    v_mastery_action := 'none';
end if;
```

对于新 Skill：

```text
v_skill_row.mastery_level = NULL
```

SQL：

```text
0 <= NULL
```

不是 true，而是 `NULL/unknown`。

所以如果 malformed trusted payload 是：

```text
新 Skill
current authoritative mastery = M1

masteryAction:
upgrade → proposedLevel = 0
```

Phase G 不会挡住。

然后 Phase H：

```text
INSERT Skill
→ DB 默认 M1

UPDATE skills
SET mastery_level = 0
```

结果：

> **普通 growth settlement 把新 Skill 从默认 M1 降到了 M0。**

但项目 ADR 明确规定：

> Mastery 是数据库级 P1 不变量；普通 settlement 必须 `new_mastery = greatest(current, proposed)`，永远不能倒退。

因此严格按你们自己设定的 authority 标准，这仍然是 P1。

正常的 `SettlementService` 当前确实不会生成这种 payload，因为它在 TS 层也使用 M1 默认值。

但问题就在于：

> **你们已经把“Mastery 单调”定义成数据库不变量，而不是“只要 TS 正常就行”。**

所以 Final Settlement Freeze 前应该补掉。

### 修法很简单

0027 不需要再重写大量逻辑。

增加一个 authoritative current mastery：

```sql
v_current_mastery integer;
```

Skill lookup 后：

```sql
v_current_mastery :=
  coalesce(v_skill_row.mastery_level, 1);
```

然后 Phase G 全部改成基于：

```text
v_current_mastery
```

而不是直接：

```text
v_skill_row.mastery_level
```

对于 verification 更推荐直接：

```text
fromLevel = authoritative current mastery
```

而不是：

```sql
greatest(client_from_level, current_mastery)
```

因为 `fromLevel` 本来描述的就是**数据库当前状态**，根本没必要信 client。

同时增加两个 DB test：

```text
new Skill + upgrade proposed M0
→ Skill 最终 M1
→ 不产生 mastery upgrade event
```

以及：

```text
new Skill + request_verification M1→M1
→ 不创建 verification
```

# P2：Secondary Skill 存在一个潜在并发 deadlock 模式

0026 只对 **primary Skill** 获取 advisory lock。

Secondary Skill 仍然直接：

```sql
insert into skills(...)
on conflict do nothing
```



理论上：

```text
Settlement A
primary = A
secondary = B

Settlement B
primary = B
secondary = A
```

同时执行，且 A/B 都是新 Skill 时，可能出现：

```text
T1 创建 A
T2 创建 B

T1 尝试插 B → 等 T2
T2 尝试插 A → 等 T1
```

PostgreSQL 最终会检测 deadlock 并中止一个事务，因此**不会破坏永久数据一致性**，所以不是 P1。

但会出现偶发 500。

以后做 Skill Tree 时最好：

> 收集 primary + secondary 全部 normalized labels → 排序 → 按固定顺序获取 advisory locks。

这样彻底消除 lock-order inversion。
