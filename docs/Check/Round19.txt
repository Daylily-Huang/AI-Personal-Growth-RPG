## 1. new-Skill Mastery NULL 漏洞：正式关闭

0027 现在明确引入：

```sql
v_current_mastery integer;
```

在 Skill lookup 后：

```sql
v_current_mastery :=
  coalesce(v_skill_row.mastery_level, 1);
```

因此：

```text
已有 Skill → 使用数据库真实 mastery
新 Skill   → authoritative mastery = M1
```

这与 `skills.mastery_level default 1` 以及 TS 的 `DEFAULT_SKILL_MASTERY = 1` 一致。

更关键的是，Phase G 已经不再直接依赖可能为空的：

```sql
v_skill_row.mastery_level
```

而统一使用：

```sql
v_current_mastery
```

所以：

```text
新 Skill
proposed M0
```

现在会命中：

```sql
0 <= 1
```

然后：

```text
masteryAction → none
```

不会出现 M1 → M0。

这已经满足项目 ADR 要求的：

> 普通 growth settlement 的 Mastery 单调增长。

```sql
v_from_level := v_current_mastery;
```

因此新 Skill M1 请求：


也不会产生无意义 pending。

# 10. 还有哪些 P2？

现在这些都不应该继续阻塞 Stage2。

### P2-A：stale pending MasteryVerification 生命周期

这里我新保留一个后续问题。

例如：

```text
Skill M1
↓
pending verification M1→M5

后来另一项高质量证据
↓
直接 upgrade 到 M5
```

当前 H.5 immediate upgrade 会：

```text
skills.mastery_level → M5
mastery_events +1
```

但没有同步把旧：

```text
pending M1→M5
```

标成：

```text
verified / rejected / superseded
```

因此 Mastery queue 可能残留已经失效的 pending。

这不是永久成长状态损坏，因为 Skill 已经正确升级；所以不升 P1。

但在你下一阶段真正把：

```text
Mastery queue
```

切到 Supabase 时，建议顺手解决。

### P2-B：Composite FK

仍然建议最终形成：

```text
(user_id, activity_id)
(user_id, assessment_id)
(user_id, skill_id)
```

数据库关系级 tenant integrity。

当前主 settlement RPC 已验证 ownership，所以 Auth/UI 阶段不是 blocker。

但是：

```text

imports
reconciliation
```

出现前最好补。

---

### P2-C：Skill alias identity

现在 TS：

```text
normalized name OR aliases
```

SQL settlement：

```text
normalized_name only
```

因此未来真正启用 alias 后必须统一。

但目前 Skill Ontology 尚未进入生产语义，所以可以留到对应阶段。

---

### P2-D：Secondary Skill lock ordering

Primary 使用 advisory lock。

Secondary 仍逐个：

```sql
insert ... on conflict do nothing
```

理论上多事务交叉 secondary/primary 可以制造 lock-order inversion。

Postgres 会 deadlock detect + rollback，不会腐化 permanent state，因此不是 Authority blocker。

Skill graph 阶段再统一：

```text
所有 skill labels
→ normalized
→ sort
→ fixed-order advisory locks
```

即可。
