# P1-2：Supabase SSR Middleware 没有正确传播 refresh cookies / cache headers

这个问题比普通 UI bug严重，因为涉及 Auth session。

当前 middleware：

```ts
setAll(cookiesToSet) {
  ...
  response.cookies.set(...)
}
```

然后如果发生 redirect：

```ts
return NextResponse.redirect(redirectUrl);
```



存在两个问题。

## 问题 A：redirect 丢掉刷新后的 cookies

`supabase.auth.getUser()` 期间可能刷新 token。

这些新 cookies 被写入变量：

```text
response
```

但登录页/未认证 redirect 时返回的是一个**全新的**：

```ts
NextResponse.redirect(...)
```

没有把：

```text
response.cookies
```

复制过去。

Supabase 官方文档当前明确要求：如果创建新的 Response，必须复制 Supabase response 的 cookies，否则浏览器与服务器 session 可能失去同步并导致 session 提前失效。

典型表现可能是：

```text
旧 token 即将过期
↓
middleware 刷新 token
↓
判断用户已登录
↓
/login → /dashboard redirect
↓
redirect 没带 refreshed cookies
↓
dashboard 再次收到旧 cookie
↓
登录状态异常 / redirect loop
```

---

## 问题 B：完全丢弃了 `@supabase/ssr` 的 cache headers

更关键的是，你们自己的 `server.ts` 注释已经写明：

> middleware 必须 merge `headers`，其中包括 `Cache-Control: private, no-store`。

但是实际 middleware 根本没接：

```ts
setAll(cookiesToSet, headers)
```

只接了：

```ts
setAll(cookiesToSet)
```



而项目使用的是：

```text
@supabase/ssr ^0.12.4
```



Supabase 当前官方高级 SSR 文档专门说明，从较新的 SSR 版本开始，token refresh 时会把防缓存 headers 传给 `setAll`；如果不应用这些 headers，在 CDN / reverse proxy 场景下可能发生非常危险的缓存 session 问题。

这是 **P1 Auth security/reliability Gate**。

### 应该怎么改

抽一个统一的：

```text
copySupabaseResponse()
```

确保：

```text
cookies
+
Cache-Control / Expires / Pragma 等 refresh headers
```

全部复制到 redirect / next response。

然后专门写 token refresh + redirect 测试。

# P2-1：但 0028 的 default privileges 是一个危险的“未来 fail-open”

虽然当前表没被打穿，但下面这句我不建议保留：

```sql
alter default privileges in schema public
grant select, insert, update, delete
on tables
to anon, authenticated, service_role;
```



这意味着未来如果新增：

```text
0029_skill_edges.sql
```

而开发者忘记同一个 migration 写：

```sql
alter table skill_edges enable row level security;
```

那么新表会自动获得：

```text
anon CRUD
authenticated CRUD
```

RLS 又默认是关闭的。

于是一个“忘记写 RLS”的错误会直接变成：

> **公网客户端可读写整表。**

这与你一直建立的 fail-closed authority 模型相反。

### 应该改成

默认：

```text
anon/authenticated = 无权限
```

每个新表显式：

```text
CREATE TABLE
↓
ENABLE RLS
↓
CREATE POLICY
↓
最后才 GRANT 所需最小权限
```

`service_role` 再单独处理。

考虑到下一阶段很可能就会出现 Skill graph / `skill_edges`，建议在创建任何 0029 新表之前解决。
