# P1-1：0030 的函数默认权限修复实际上是无效的

这是本轮最重要的发现。

0030 写的是：

```sql
alter default privileges
in schema public
revoke execute on functions
from public, anon, authenticated;
```



看起来合理，但 PostgreSQL 的语义不是这样。

PostgreSQL 官方文档明确说明：

> **per-schema default privileges 只能在 global default 上“增加”权限，不能撤销 global 已经授予的权限。**

而 PostgreSQL 对新建 function 默认就有：

```text
PUBLIC EXECUTE
```

官方甚至专门拿你现在这条 SQL 当反例：

```sql
ALTER DEFAULT PRIVILEGES
IN SCHEMA public
REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;
```

官方说明这种写法**没有效果**，除非它只是撤销之前同样的 per-schema GRANT。要真正去掉新函数默认的 `PUBLIC EXECUTE`，必须改 **global default privileges**。

所以当前：

```sql
0030_function_default_privileges_tighten.sql
```

并没有实现摘要所声称的：

> “未来新增任何 RPC 默认对公网不可执行。”



---

## 正确写法

应该类似：

```sql
alter default privileges
revoke execute on functions
from public;
```

注意：

```text
不要加 IN SCHEMA public
```

然后按实际 function-owner 角色处理。

例如如果 migrations 通常由 `postgres` 创建对象：

```sql
alter default privileges
for role postgres
revoke execute on functions
from public;
```

然后 service role 是否需要自动 EXECUTE，可以单独：

```sql
alter default privileges
for role postgres
grant execute on functions
to service_role;
```

关键是：

> **global REVOKE PUBLIC EXECUTE**

而不是 schema-local revoke。

---

## 更重要：必须写真实 DB 测试，不要只 grep migration

这次 0030 为什么能“测试通过”却仍然错？

因为 `supabase-schema.test.ts` 很可能只检查：

```text
文件存在
字符串存在
migration order
```

而没有实际创建一个新函数再检查权限。

真正应该增加：

```sql
create function public.__future_rpc_probe()
returns int
language sql
as $$ select 1 $$;
```

然后：

```sql
select has_function_privilege(
  'public',
  'public.__future_rpc_probe()',
  'EXECUTE'
);
```

必须：

```text
false
```

同时：

```text
authenticated = false
anon = false
service_role = true
```

最后 drop probe。

这才叫真正验证 **future function fail-closed**。

### 这一项是 P1

```text

```

如果开发者漏写 REVOKE，那函数会默认被 PUBLIC 执行。

而这些很可能都是：

```text

```

所以这不能降成普通 hardening。
