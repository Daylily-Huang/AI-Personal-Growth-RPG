# P1：CI 现在用了假的 Supabase API keys

真正剩下的问题就在这里。

当前 CI：

```yaml
NEXT_PUBLIC_SUPABASE_URL: http://127.0.0.1:54321

NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY:
  sb_publishable_test_key

SUPABASE_SECRET_KEY:
  test_secret_key
```



这两个看起来是占位符，不是 `supabase db start` 实际启动出来的本地 key。

而你的 production HTTP E2E 并不是只判断环境变量“存在”。

它真的会拿：

```ts
const SUPABASE_PUBLISHABLE_KEY =
  process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY || ...

const SUPABASE_SERVICE_ROLE_KEY =
  process.env.SUPABASE_SECRET_KEY || ...
```

去创建真实 Supabase clients，然后：

```text
signUp()
signInWithPassword()
refreshSession()
```

并访问本地 Supabase Auth。上一轮检查的真实 E2E 就是这么工作的。

因此 CI 中显式设置：

```text
sb_publishable_test_key
test_secret_key
```

反而会覆盖测试里可能存在的本地 fallback。

也就是说 fresh CI 的真实行为很可能是：

```text
supabase db start
↓
真正的 local anon/publishable/service key = A/B
↓
CI env 强行设置 fake key = X/Y
↓
E2E createServerClient(..., X)
↓
调用 Auth
↓
Kong/Auth 拒绝无效 API key
```

这和：

```text
pnpm build
```

阶段不同。

Build 阶段只需要这些 env “长得像存在”，假的值通常也能 build。

但是 E2E 阶段是真网络调用，因此必须是真 key。

---

# 正确修法

不要手写：

```yaml
sb_publishable_test_key
test_secret_key
```

应该从正在运行的 local Supabase stack 获取实际值。

例如在 CI 中从：

```bash
supabase status -o env
```

导出真实本地环境变量。

大致模式：

```yaml
- name: Start local Supabase
  run: supabase db start

- name: Export local Supabase credentials
  run: |
    supabase status -o env >> "$GITHUB_ENV"
```

然后根据 CLI 实际输出的变量名映射到项目需要的：

```text
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
SUPABASE_SECRET_KEY
```

如果 CLI 输出的是 legacy：

```text
ANON_KEY
SERVICE_ROLE_KEY
API_URL
```

则明确映射。

核心原则：

> **E2E 必须使用刚刚启动的那个 Supabase instance 的真实 credentials。**
