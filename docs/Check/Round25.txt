# P1-3：`parent_quest_id` 存在跨租户引用漏洞

当前数据库：

```sql
parent_quest_id uuid references public.quests(id)
```

只有普通 FK。

但是 RLS 对 Quest 是：

```sql
INSERT own
UPDATE own
DELETE own
SELECT own
```

也就是 authenticated 用户对自己的 Quest 行拥有完整 CRUD。

于是理论上 User A 可以创建：

```text
child.user_id = User A
child.parent_quest_id = User B 的 Quest UUID
```

RLS 只检查：

```text
child.user_id = auth.uid()
```

不会证明：

```text
parent.user_id = auth.uid()
```

你们在 Stage2 已经遇到过完全相同的问题：

> Activity 的 `quest_id` 必须额外检查 Quest ownership。

Quest 自己的 parent-child 现在也需要同样的 tenant integrity。

API 里写：

> “validate parent relations”

不够。

因为 authenticated client 可以绕过 Next API，直接调用 Supabase Data API。

### 正确方案

建议加 DB 级 composite integrity：

```sql
unique (user_id, id)
```

然后父级关系本质上约束：

```text
(child.user_id, child.parent_quest_id)
        ↓
(parent.user_id, parent.id)
```

或者用强制 trigger 验证。

总原则：

> **跨租户父子 Quest 必须在 DB 层成为“不可能状态”。**

# P1-4：Quest Tree 可以形成环

当前 schema 没有防：

```text
A.parent = A
```

也没有防：

```text
A → B
B → A
```

更没有防：

```text
A → B → C → A
```



而你的摘要声称存在：

```ts
syncParentQuestProgress(...)
```

并且是：

> recursively recalculates parent progress



如果数据库里存在 cycle，最直接的结果就是：

```text
sync A
→ parent B
→ parent A
→ parent B
→ ...
```

最终：

```text
stack overflow
无限递归
事务失败
```

即使 API 创建时做 cycle validation，也仍然不够——因为 Quest 当前是 client-writable。

### 必须增加

至少：

- self-parent reject；
- descendant-parent reject；
- recursion visited-set 防御；
- 测试：
  - A → A
  - A → B → A
  - A → B → C → A。

更稳的是 DB trigger / recursive CTE constraint logic。

# P1-5：所谓“自动聚合 progress”目前不是 authoritative derived state

这是一个更深的设计问题。

当前 Quest RLS 允许 authenticated：

```sql
UPDATE quests
```



而 `progress` 就是普通列：

```sql
progress numeric not null default 0
```



所以即使：

```ts
syncParentQuestProgress()
```

每次都会正确算：

```text
Parent = children aggregation
```

用户仍然可以绕开 Next API：

```text
PATCH Supabase Data API

progress = 1
status = completed
```

直接把 Main Quest 打成 100%。

于是你现在同时声明了两个相互冲突的模型：

### 模型 A

```text
parent.progress 是 children 推导值
```

### 模型 B

```text
parent.progress 是用户可直接编辑字段
```

两者必须选一个。

我的建议：

### Leaf Quest

允许用户修改：

```text
progress
status
```

### 有 children 的 Parent / Main / Boss

`progress` 应是：

```text
derived state
```

客户端不可任意写。

可以：

- DB trigger 自动 roll-up；
- SECURITY DEFINER RPC；
- 或干脆不持久化 parent progress，读取时 compute。

否则“automatic progress roll-up”只是 UI 约定，不是系统 invariant。
