# P1-1：Parent/Main/Boss progress 仍然可以被客户端直接伪造

这是当前最严重的 Quest authority 问题。

现有 RLS 仍然给 authenticated 用户自己的 `quests`：

```sql
SELECT
INSERT
UPDATE
DELETE
```

完整权限。

而 `SupabaseRepository.updateQuest()` 直接允许：

```ts
status
questSize
progress
isMainQuest
isBoss
...
```

全部写数据库。

HTTP PATCH 也直接接收：

```ts
body.status
body.questSize
body.progress
```

然后 `repo.updateQuest()`。

问题在于 0032 的 DB trigger 只做：

> 当一个 child 改变时，重新计算它的 **parent / ancestors**。

它没有做到：

> 当用户直接改 parent 自己的 progress 时，强制用 children 重算 parent 自己。

所以一个有 10 个 child、真实进度 20% 的 Main Quest，authenticated 用户仍然可以绕开 Next API，直接：

```text
UPDATE quests
SET progress = 100,
    status = 'completed'
WHERE id = main_quest_id;
```

RLS 会允许。

更糟的是，如果 Main 还有 grandparent，这个伪造的 `100%` 还会被 trigger 当真，继续 roll-up。

这意味着报告里所说的：

> “Authoritative Derived Progress Roll-Up”

目前只完成了 **automatic roll-up**，没有完成 **authoritative derived state**。

### 正确方向

用户可编辑：

```text
title / description / deadline / metadata
```

系统推导：

```text
parent progress
parent completion
Boss/Main aggregate progress
```

这两类字段必须分开 authority。

我建议不要再让 authenticated 对整行拥有 unrestricted UPDATE。至少把 parent-derived `progress/status` 移到 server-owned RPC，或者让 DB 对“有 children 的 Quest”拒绝客户端直接修改这些字段。

# P1-2：新的 composite FK 把“删除父 Quest”搞坏了

0032 写的是：

```sql
foreign key (user_id, parent_quest_id)
references public.quests(user_id, id)
on delete set null;
```



这里有一个很隐蔽的 PostgreSQL 语义问题。

对于 composite FK：

```text
(user_id, parent_quest_id)
```

不指定 column list 的：

```sql
ON DELETE SET NULL
```

默认会把 **两个 referencing columns 全部置 NULL**。

也就是：

```text
user_id = NULL
parent_quest_id = NULL
```

但 `quests.user_id` 是：

```sql
NOT NULL
```

因此：

> **删除一个仍有 child 的 parent Quest 会失败。**

PostgreSQL 官方文档明确说明 composite FK 的 `SET NULL` 默认处理全部 referencing columns；如果 tenant ID 不能置 NULL，应明确只指定可空列。

正确写法应类似：

```sql
ON DELETE SET NULL (parent_quest_id)
```

你们现有测试没有发现，是因为测试删除的是 leaf/subquest，并没有：

```text
Parent
 └─ Child

DELETE Parent
```

这种 case。 

这是确定性的 P1，不是理论问题。

# P1-3：Reparent 会留下旧 Parent 的脏进度，而且并发 roll-up 不安全

0032 现在：

```sql
v_parent_id :=
  coalesce(NEW.parent_quest_id, OLD.parent_quest_id);
```



假设：

```text
Parent A
  └─ Child X

Parent B
```

把 X 从 A 移到 B：

```text
OLD.parent = A
NEW.parent = B
```

`coalesce(B,A)` 得到：

```text
B
```

于是只重新计算 B。

**A 永远不会被重新计算。**

API 层也同样：

```ts
const updated = await repo.updateQuest(...)
if (updated.parentQuestId) {
  await syncParentQuestProgress(repo, updated.parentQuestId)
}
```

只同步 new parent。

因此：

```text
A 原来 progress = 50
Child X 被移走
A 应该变化
实际仍然 = 50
```

这是直接破坏 derived-state invariant。

此外 SQL trigger 在计算 children average 前：

```sql
select * into v_current_parent
from quests ...
```

没有：

```sql
FOR UPDATE
```

两个 sibling 并发更新时，可以分别用各自看见的旧 sibling snapshot 算 progress，再互相覆盖 parent。当前没有 Quest concurrency test。

### 修复

最好做一个 DB helper：

```text
recompute_quest_chain(user_id, parent_id)
```

reparent 时同时：

```text
recompute OLD parent chain
recompute NEW parent chain
```

并且在计算 children aggregate 前锁定 parent row。

# P1-4：Demo 与 Production 已经出现两套 Quest Growth Rule

这一项尤其违反你们之前坚持的：

> Repository 不应该保存 business rules。

Demo settlement：

```text
progressAdvance
= effectiveMinutes / 2
= minimum 10
= maximum 100
```

例如有效学习 50 分钟：

```text
+25%
```



但 PostgreSQL settlement：

```sql
coalesce(round(activity.completion * 100), 20)
```



而正常 HTTP 创建 Activity 根本没有传：

```text
completion
```

只传：

```text
rawInput
questId
totalMinutes
effectiveMinutes
```



AI Assessment persistence 也只保存 Assessment、把 Activity 变成 assessed，没有把 AI 的 `proposal.activity.completion` 写回 Activity。

所以生产实际行为基本变成：

```text
每次 linked Activity settlement
= Quest 固定 +20%
```

而 Demo：

```text
40 effective min → +20
50 effective min → +25
120 effective min → +60
```

这意味着完全相同的 Growth Loop：

```text
Demo ≠ Supabase production
```

现有测试故意只写：

```ts
expect(progress).toBeGreaterThan(0)
```

因此没有发现这个 divergence。

### 正确架构

Quest progress delta 应该只有**一份 deterministic business rule**。

比如：

```ts
calculateQuestProgressDelta(...)
```

放到 domain/Growth Engine。

SettlementService 算好：

```text
questProgressDelta
```

然后：

```text
DemoRepository → apply exact delta
Supabase RPC   → apply exact delta
```

DB 负责：

```text
ownership
idempotency
atomicity
bounds
roll-up
```

不要让 DB 和 Demo 各自发明一套 progression algorithm。

# P1-5：QuestSize 已影响永久 XP，但没有被冻结/写入 Ledger

这是 Stage4 接入 Growth Engine 后出现的新 authority 问题。

现在流程：

```text
SettlementService
↓
repo.getQuest(activity.questId)
↓
读取当前 quest.questSize
↓
calculateXp()
↓
稍后调用 settle_activity()
```



但 Quest 本身还是 authenticated 可 UPDATE 的。

所以存在窗口：

```text
SettlementService 读到 questSize = main
↓
算 XP
↓
另一个请求把 Quest 改成 micro
↓
settle_activity 写入刚才算出的 XP
```

数据库根本没有验证：

```text
用于计算 XP 的 QuestSize
==
settlement 时 authoritative QuestSize
```

这和你们 Stage2 当年修掉的 repetition stale snapshot 是同一类问题。

而且 Ledger 里目前记录：

```text
rulesVersion
modifiers
amount
...
```

但 `XpModifiers` 本身没有 `questSize` / `questCap`。

因此半年以后用户把 Quest size 从：

```text
standard → main
```

你甚至无法从 Ledger 精确还原：

> 为什么这笔 XP 当时被 cap 到这个数？

更糟的是 Quest 可以硬删除，而 Activity FK 是：

```sql
quest_id references quests(id) on delete set null
```



一旦删掉 Quest，Activity 的 quest relationship 也消失。

这已经影响到 **永久 XP 的历史可审计性**。

### 推荐做法

最干净的是 Activity 创建时冻结：

```text
quest_id
quest_size_snapshot
```

类似：

```text
rules_version
```

Settlement 永远使用 Activity 冻结的 snapshot。

Ledger 再保存：

```text
quest_id_snapshot
quest_size_snapshot
quest_cap
```

至少 modifier JSON 也必须包含这些。

对于已经参与 confirmed settlement 的 Quest，建议不要物理 DELETE，改成：

```text
archived
```
