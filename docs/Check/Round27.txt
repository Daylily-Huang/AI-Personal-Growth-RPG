# P1：0033 新增了一个跨租户 SECURITY DEFINER RPC 漏洞

这是本轮唯一真正阻塞冻结的问题。

0033 创建：

```sql
public.recompute_quest_chain(
    p_user_id uuid,
    p_parent_id uuid
)
```

而且它是：

```sql
SECURITY DEFINER
```

内部可以：

```sql
select ...
from public.quests
where user_id = p_user_id
for update;

update public.quests ...
```

也就是说，这个函数具有跨 RLS 的 DB owner 权限。

问题出在 0033 最后：

```sql
revoke all on function
public.recompute_quest_chain(uuid, uuid)
from public, anon, authenticated;

grant execute on function
public.recompute_quest_chain(uuid, uuid)
to service_role, authenticated;
```



你先 revoke authenticated，然后**马上又 grant 回去了**。

---

## 攻击面非常明确

User A 可以调用：

```text
RPC recompute_quest_chain(
    p_user_id = User B UUID,
    p_parent_id = User B Quest UUID
)
```

因为：

```text
p_user_id
```

是调用方自己传入的，而不是：

```sql
auth.uid()
```

函数又是 `SECURITY DEFINER`。

所以函数内部不会受到 User A 的 RLS 限制。

结果：

> authenticated 用户拥有调用高权限函数修改其他租户 Quest 派生状态的能力。

虽然它不能随便写任意数字，只能按 B 的 children 重算，但依然是明确的：

```text
cross-tenant unauthorized write
```

而且可以改：

```text
progress
status
completed_at
updated_at
```

并获取/占用其他用户 Quest 行锁。

这是不能 Frozen 的权限边界漏洞。

---

## 修复非常简单

0034：

```sql
revoke all
on function public.recompute_quest_chain(uuid, uuid)
from public, anon, authenticated;

grant execute
on function public.recompute_quest_chain(uuid, uuid)
to service_role;
```

甚至如果除了 trigger/internal function 根本没人需要直接 RPC 调它，连 `service_role` 外部 grant 都可以不要。

核心是：

> **绝不能 grant authenticated。**

然后加 live DB test：

```text
set role authenticated
JWT = User A

call recompute_quest_chain(User B, User B parent)
→ permission denied
```

同时验证：

```text
User A 正常 PATCH 自己 child
→ DB trigger
→ internal recompute
→ Parent 正常更新
```

这样才能证明：

```text
外部不可调用
内部 trigger 仍能工作
```

# P2-2：failed / archived Parent 仍然可能被“复活”

`settle_activity` 对直接绑定 Quest 的保护确实存在：

```sql
if quest.status not in ('archived', 'failed')
```

才推进。

这一层没问题。

但 parent roll-up 不是这样。

`recompute_quest_chain()`：

```sql
v_new_status :=
case
  when v_all_completed
       and v_avg_progress = 100
    then 'completed'
```

没有先判断：

```text
parent.status = failed
parent.status = archived
```



因此：

```text
Main Quest = failed

├─ Child A completed
└─ Child B completed
```

任意 child 更新触发 recompute 后：

```text
failed
→ completed
```

同样：

```text
archived
→ completed
```

这是明显生命周期语义错误。

### 建议

在 `recompute_quest_chain` 最前面：

```text
如果 parent.status ∈ {failed, archived}
→ 不允许 roll-up 改变它的 terminal status
```

到底 progress 要不要继续统计可以另定，但：

```text
failed / archived
```

至少不应被自动改成 `completed`。

# P2-3：“并发测试”实际上没有测试真正并发连接

报告声称：

> 并发 4 兄弟任务并行更新、无丢失、无死锁。



测试代码确实：

```ts
await Promise.all([
  client.query(...),
  client.query(...),
  client.query(...),
  client.query(...),
]);
```



但这里四个 query 全部使用**同一个 `pg.Client`**。

单个 PostgreSQL connection 无法同时执行四个独立 transaction/query；node-postgres 会在同一连接上排队。

所以它验证的是：

```text
快速连续提交 4 次
```

不是：

```text
4 个并发 transaction
同时竞争 parent row
```

`FOR UPDATE` 的实现方向是对的，因此我没有把它升成 P1。

但真正的 concurrency gate 应该使用：

```text
4 个独立 Client / Pool connection
```

让它们真正竞争同一个 parent。
