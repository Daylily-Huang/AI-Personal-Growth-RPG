  p_quest_id: input.questId,

这才是当前真实 Growth Loop 使用的 RPC。

但是 0034 为了实现：

```text

    text,

    uuid
);

随后创建：

CREATE OR REPLACE FUNCTION public.create_activity(

  p_description text,
  p_domain_id text,
  p_started_at bigint,
  p_ended_at bigint,
  p_quest_id uuid DEFAULT NULL

RETURNS uuid
```



这根本不是当前 `create_activity` 的签名。

所以它没有：

> replace 当前生产 RPC

# 更严重的是，这个新 overload 使用了不存在的 Activity schema

0034 这个新函数内部写：

```sql
INSERT INTO public.activities (
    user_id,
    title,
    description,
    domain_id,
    started_at,
    ended_at,
    ...
)
```



但当前 authoritative Activity 表实际上是：

```sql
title
raw_input
activity_type
started_at
ended_at
total_minutes
effective_minutes
completion
rules_version
...
```

根本没有：

```text
description
domain_id
```



也就是说新 RPC 是来自另一版 schema/旧设计的函数。

如果真正调用这条 overload，会在运行阶段失败。

而 PL/pgSQL 中具体 SQL command 通常是在首次执行相关语句时才进行完整 parse/analysis，因此仅仅 migration 成功、甚至 `db reset` 成功，并不能证明这个函数体能真正执行。PostgreSQL 官方文档也明确描述了 PL/pgSQL SQL command 的这种延迟解析行为。

所以报告里的：

```text

```

不能证明这个函数是正确的。
