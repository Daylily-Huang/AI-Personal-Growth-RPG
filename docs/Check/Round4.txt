# 二、P1：Repository port 现在其实还不能直接支持 Supabase

这是我认为下一步最先要修的。

当前接口是：

```ts
getActivity(id): Activity | null;
listActivities(): Activity[];
getPlayer(): PlayerState;
applySettlement(...): SettlementResult;
```

全部是**同步接口**。

Demo JSON 当然没问题，因为：

```ts
fs.readFileSync()
```

但是 Supabase 是远程数据库。

真实 SupabaseRepository 必然类似：

```ts
await supabase
  .from(...)
  .select(...)
```

所以未来根本不可能保持：

```ts
getPlayer(): PlayerState
```

必须是：

```ts
getPlayer(): Promise<PlayerState>
```

这意味着目前这句话：

> “SupabaseRepository 实现同一 Repository port，SettlementService 完全不用变”

**严格来说还不成立。**

---

## 应该现在就改

Repository 应该从第一天就定义成 async port：

```ts
interface Repository {
  getActivity(id: string): Promise<Activity | null>;

  getAssessment(id: string): Promise<Assessment | null>;

  listTransactions(): Promise<XpTransaction[]>;

  getSkill(name: string): Promise<SkillState | null>;

  getPlayer(): Promise<PlayerState>;

  applySettlement(
    settlement: SettlementToApply
  ): Promise<SettlementResult>;
}
```

DemoRepository 即使内部同步读 JSON，也可以：

```ts
async getPlayer() {
  return this.readDb().player;
}
```

然后：

```ts
SettlementService.confirmAssessment()
```

也改成：

```ts
async confirmAssessment(...)
```

这一刀应该**现在改**。

不要等 Supabase 写到一半才被迫重构所有 service / route / test。

# 三、P1：更严重——现在的 transaction boundary 有 lost update 风险

这个问题非常重要。

当前 `SettlementService` 是先在 Repository 外部读取：

```ts
const currentSkill = repo.getSkill(...)
const player = repo.getPlayer()
```

然后计算：

```ts
primarySkill.xp =
  currentSkill.xp + xp

updatedPlayer.totalXp =
  player.totalXp + xp
```

最后才：

```ts
repo.applySettlement(settlement)
```



而 `SettlementToApply` 传进去的已经是**算好的绝对状态**：

```ts
primarySkill: SkillState
player: PlayerState
```



DemoRepository 最后直接：

```ts
db.skills[...] = settlement.primarySkill
db.player = settlement.player
```



---

# 这会造成什么？

假设：

```text
当前 total XP = 100
```

两个**不同 assessment**同时结算：

### A

```text
读到 100
+20
→ 算出 120
```

### B

也同时：

```text
读到 100
+30
→ 算出 130
```

然后：

```text
A 写入 120
B 写入 130
```

最后：

```text
Ledger:
+20
+30

理论 total XP:
150

实际 Player:
130
```

这叫：

# **lost update**

而：

```sql
UNIQUE(assessment_id)
```

救不了这个问题。

因为：

```text
assessment A
assessment B
```

本来就是两个不同 ID。

---

# 所以真正的事务边界应该调整

不能只是：

```text
业务层先算完全部最终状态
↓
数据库事务负责“写进去”
```

应该是：

```text
取得当前 authoritative state
↓
计算/校验
↓
写 ledger
↓
更新 skill
↓
更新 player
↓
更新 assessment
↓
commit
```

这个过程必须保证没有其他 settlement 在中间修改状态。

---

## 我建议下一步采用

至少把 `SettlementToApply` 从：

```ts
player: PlayerState
primarySkill: SkillState
```

逐渐改成类似：

```ts
xpDelta: number

primarySkill: {
  name: string;
  xpDelta: number;
  masteryCandidate?: ...
}

transaction: ...
```

不要让 Service 拿旧数据算出：

```text
totalXp = 130
```

然后 Repository 无脑覆盖。

Repository / DB 应执行：

```text
current total
+
delta
```

或者使用 version / optimistic concurrency。

Supabase 阶段还需要真正设计：

```text
transaction
或
DB RPC / atomic settlement function
```

而不是连续调用五六个 `.update()`。
