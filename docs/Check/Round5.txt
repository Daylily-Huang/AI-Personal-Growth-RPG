我继续查了，但先明确一点：**GitHub 当前 `main` 仍然是 `0384465b`，没有比 Round4 更新的 commit**。你这次上传的也是同一份 Milestone 2.6 摘要。

所以这一轮不是“新 diff 验收”，而是我对当前版本做了更深的 **Growth Loop + Supabase 前置完整性审查**。结果是：又发现了一个必须优先修的核心漏洞，以及几个现在处理成本很低、以后处理成本会很高的问题。

# 结论

## 当前 `0384465b`：**Milestone 2.6 PASS**
## 直接开始正式 Supabase：**仍建议暂缓一个很短的 Milestone 2.7**

而且这次我认为优先级第一的问题已经不是 optimistic concurrency，而是：

# P1：同一个 Activity 目前可以被重复 Assessment，并重复发 XP

这个问题比较严重。

现在 `/api/activities/[id]/assess` 的逻辑是：

```text
找到 Activity
↓
调用 AI
↓
repo.addAssessment()
```

没有检查：

```text
这个 Activity 是否已经 assessed？
是否已有 pending assessment？
是否已经 confirmed？
```



而 `DemoRepository.addAssessment()` 同样只是继续插入一个新 Assessment，并没有阻止同 Activity 多 Assessment；`applySettlement()` 又只检查 Assessment 自己是不是 `pending`，并没有检查这个 Activity 是否已经被另一 Assessment 结算。此前读取到的实现正是这种结构。

于是理论上可以：

```text
Activity A
   ↓
Assessment 1
   ↓ Confirm
+20 XP

Activity A
   ↓ 再调用 assess
Assessment 2
   ↓ Confirm
+20 XP
```

当前数据库保护只有：

```sql
UNIQUE(assessment_id)
```

它只能阻止：

```text
Assessment 1
→ Confirm 两次
```

却阻止不了：

```text
同一个 Activity
→ Assessment 1
→ Assessment 2
→ 分别 Confirm
```

这正好属于你项目治理文档明确举出的 **Bug**：

> “一个 Activity 加了两次 XP。”



这应该在 Supabase 前修。

# 我建议不要简单规定“一 Activity 只能一 Assessment”

因为以后你可能需要：

```text
AI 第一次判断不准
↓
用户 Edit / Re-assess
↓
生成 Assessment revision 2
```

这属于合理需求。

更好的不变量是：

> **一个 Activity 可以拥有多个 Assessment revision，但一个 Activity 最多只能产生一笔原始 Activity XP settlement。**

数据库层可以最终做成类似：

```sql
create unique index xp_transactions_one_activity_settlement_idx
on xp_transactions(activity_id)
where xp_type = 'activity';
```

而：

```text
adjustment
correction
rollback
```

仍可以另起交易。

同时服务端 Confirm 再检查：

```text
activity.status === confirmed
→ already_settled
```

形成应用层 + DB 层双保险。

# P1：上一轮发现的 concurrent repetition 问题仍然存在

这个没有新 commit，所以当然也还没有修。

# P1：Rules Version 现在并没有真正“冻结规则”

这个是本轮深挖中新发现的另一个长期风险。

你的治理规范明确规定：

> **新规则只作用于新 Activity。**



也就是说：

```text
Activity A 创建时
Growth Rules = v0.1
```

即使两天以后系统升级：

```text
Growth Rules = v0.2
```

Activity A 原则上也不该被 v0.2 偷偷重新裁决。

但当前：

```ts
Activity
```

根本没有：

```ts
rulesVersion
```

字段。

Assessment 虽然记录了：

```ts
rulesVersion
```

但 Confirm 时真正执行的是：

```ts
calculateXp(...)
```

也就是**部署时当前代码里的 Growth Engine**。

所以未来会出现：

```text
Activity 创建于 v0.1
Assessment 创建于 v0.1

系统部署 v0.2

用户再 Confirm
↓
实际用 v0.2 calculateXp()
```

然后 Transaction 还记录成 v0.2。

这会破坏历史规则审计。

---

## 推荐现在就确定一个原则

### 推荐方案：Activity 创建时绑定 rulesVersion

```ts
Activity {
  ...
  rulesVersion: "growth-engine-v0.1"
}
```

然后 Confirm：

```ts
getEngine(activity.rulesVersion)
```

未来可以形成：

```ts
growthEngines = {
  "growth-engine-v0.1": calculateXpV01,
  "growth-engine-v0.2": calculateXpV02,
}
```

至少在还只有 v0.1 时把数据字段和边界设计好。

否则等你已经积累一年成长数据以后再处理规则版本迁移，会麻烦很多。

# Mastery pending unique 还有一个更细的坑

文档建议：

```sql
unique(skill_id)
where status = 'pending'
```



但当前 migration 中：

```sql
skill_id uuid
```

是 nullable。

PostgreSQL 普通 UNIQUE 对多个 `NULL` 并不会按“同一个值”阻止。

所以如果：

```text
skill_id = NULL
```

你仍可能得到：

```text
Statistics pending #1
Statistics pending #2
Statistics pending #3
```

因此正式 schema 最好不要依赖 nullable `skill_id`。

推荐：

```text
MasteryVerification
必须绑定真实 skill_id
```

并让：

```sql
skill_id uuid not null
```

然后 unique 至少应考虑：

```sql
(user_id, skill_id)
WHERE status='pending'
```

```ts
skills: Record<string, SkillState>
```

Skill 身份就是：

```text

```



但是正式数据库已经想要：

```text

```

与此同时 AI 又可以自由产生：

```text

Regression Analysis

```

所以现在是很好的时机确定：

```text

Skill name = 可编辑显示名称
Aliases = AI 匹配辅助
Domain = 分类
```

不要在 SupabaseRepository 里把：

```text

```

当数据库主身份。

否则以后改个名字都会非常痛苦。

# Multi-skill 还有一个必须明确、但不是立刻的 Bug

当前：

```ts
affected_skills[0]
```

是 primary skill。

只有它真正拿 XP、Mastery。其他技能主要被创建节点和 relation。

这个并非一定错误，但必须明确成产品规则。

你有两个方案：

**A. MVP primary-only**

```text
总 XP → 100% primary skill
secondary skills 只记录关联/证据
```

优点：简单，不膨胀 XP。

**B. weighted allocation**

例如：

```text
Total XP = 50

Statistics 70% → 35
R          30% → 15
```

必须保证：

```text
35 + 15 = 50
```

绝不能：

```text
Statistics +50
R +50
```

否则凭空生成双倍 XP。

**我推荐 MVP 继续 A，但明确写入规则文档。**
