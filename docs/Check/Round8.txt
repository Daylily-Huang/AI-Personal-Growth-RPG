# 一、最严重的问题：当前登录用户可以直接给自己刷 XP / Mastery

这属于我这轮的 **P0（部署前 blocker）**。

`0017_rls.sql` 对所有 private table 统一生成了：

```sql
SELECT
INSERT
UPDATE
DELETE
```

四种 own-row policy。

而名单里包括：

```text
player_states
skills
xp_transactions
mastery_verifications
mastery_events
```



这意味着 RLS 当前解决的是：

```text
User A 不能修改 User B
```

但没有解决：

```text
User A 能不能绕过游戏规则修改 User A 自己
```

而答案目前是：

# **可以。**

理论上登录用户拿浏览器里的 publishable key + 自己的 JWT，就可以尝试直接：

```text
player_states.total_xp = 999999
```

或者：

```text
skills.mastery_level = 10
```

甚至：

```text
INSERT xp_transactions (...)
```

或：

```text
DELETE xp_transactions
```

因为当前 RLS 的判断只是：

```sql
user_id = auth.uid()
```

只要是“我的数据”，就允许 UPDATE / INSERT / DELETE。

---

# 这为什么特别严重？

因为我们前面六轮一直坚持的核心架构是：

```text
AI
↓
Proposal

User
↓
Confirm

Growth Engine
↓
Deterministic calculation

Server settlement
↓
XP Ledger
```

而现在数据库打开了一条后门：

```text
Browser
↓
Supabase Data API
↓
UPDATE skills
SET mastery_level = 10
```

等于绕过了整套：

```text
Evidence
Growth Engine
Mastery Verification
Repetition
Settlement
Ledger
```

所以：

> **RLS ≠ 游戏规则安全。**

RLS 只解决“谁的数据”，还必须解决：

> **这个用户对自己的哪些数据有权直接修改？**

这是本轮最重要的发现。

# 二、RLS 应该改成“权限矩阵”，不能所有表一刀切

现在：

```text
所有 private tables
→ SELECT
→ INSERT
→ UPDATE
→ DELETE
```

这个设计必须拆开。

我建议至少变成：

| Table | 用户直接 SELECT | 用户直接 INSERT | UPDATE | DELETE |
|---|---:|---:|---:|---:|
| profiles | ✅ | ❌/trigger | ✅有限 | ❌ |
| player_states | ✅ | ❌ | ❌ | ❌ |
| domains | ✅ | ✅ | ✅ | ✅ |
| quests | ✅ | ✅ | ✅ | ✅ |
| activities | ✅ | ✅ | ⚠️有限 | ⚠️有限 |
| ai_assessments | ✅ | ❌/server | ❌ | ❌ |
| evidence_records | ✅ | ⚠️ | ⚠️ | ⚠️ |
| skills | ✅ | ❌核心字段 | ❌核心字段 | ❌ |
| xp_transactions | ✅ | **❌** | **❌** | **❌** |
| mastery_verifications | ✅ | ❌ | ❌ | ❌ |
| mastery_events | ✅ | **❌** | **❌** | **❌** |
| knowledge/artifacts | ✅ | ✅ | ✅ | ✅ |
| reviews | ✅ | ✅ | ✅ | ✅ |

尤其：

```text
xp_transactions
```

应该是真正意义上的：

# **用户只读账本**

普通 authenticated session：

```text
SELECT ✅
INSERT ❌
UPDATE ❌
DELETE ❌
```

只能通过之后的：

```text
settle_activity RPC
```

写入。

# 五、第二个 P1：Evidence schema 出现明显 Code ↔ DB 漂移

这个是明确 bug。

数据库：

```sql
evidence_level integer
check (evidence_level between 0 and 4)
```



但 AI schema 明确允许：

```ts
level:
z.number()
 .int()
 .min(0)
 .max(6)
```



Growth Engine 也明确：

```text
Evidence = E0 … E6
```

并存在：

```text
E0
E1
E2
E3
E4
E5
E6
```

七档 modifier。

所以现在：

```text
AI Proposal:
Evidence = E5
✅ Zod 合法

Growth Engine:
E5
✅ 合法

数据库 evidence_records:
E5
❌ CHECK violation
```

这是典型的 Spec → Code → DB 不一致。

### 应该修成

如果你们现行宪法确实是 E0–E6：

```sql
check (
  evidence_level between 0 and 6
)
```

并加静态 invariant test：

```text
AI Evidence range
=
Growth Engine range
=
Database range
```

这一项建议 **Stage2 前修**。

# 六、第三个 P1：user_id RLS 还不能保证“引用对象也是我的”

这是多租户数据库很容易忽略的问题。

比如：

```sql
skills {
    user_id
    domain_id references domains(id)
}
```



当前 RLS insert 只检查：

```sql
skills.user_id = auth.uid()
```

并没有数据库 invariant 保证：

```text
skill.user_id
=
domain.user_id
```

类似问题还有：

```text
activities → quest
ai_assessments → activity
knowledge_edges → source/target nodes
artifact_links → artifact
mastery events → skill/activity
```

例如 knowledge edge 有：

```sql
user_id = A
source_node_id = 某 UUID
target_node_id = 某 UUID
```

FK 只验证节点 ID 存不存在，并不编码：

```text
这个 node 也必须属于 A
```



---

## 最稳妥的数据库设计

重要 tenant-owned FK 使用组合约束：

```text
(user_id, id)
```

例如 Parent：

```sql
unique (user_id, id)
```

Child：

```sql
foreign key (user_id, activity_id)
references activities(user_id, id)
```

这样数据库直接保证：

> A 的 Assessment 永远不能指向 B 的 Activity。

不仅依靠应用层“应该不会这么做”。

这个对于你将来的：

```text
SupabaseRepository
+
RPC
+
multi-user
```

非常重要。

```sql
activity_id uuid not null,

skill_id uuid,

domain_id uuid
```

这在早期 0009 单独存在时还能理解，因为以前相应 migration 不完整。

但现在：


```text
activity_id → activities
assessment_id → ai_assessments
skill_id → skills
```

哪些必须有 FK。

我建议：

```text

activity_id
```

否则数据库可以出现：

```text
XP transaction
→ 指向一个根本不存在的 Activity
```

对于“审计账本”不是好事。

# 八、Skill Identity 在 PostgreSQL 还少最后一层并发保护

Demo 端之前已经做得不错：

```text
normalized label
→ same stable UUID
```

但现在数据库 `skills` 表只有：

```sql
id
user_id
name
aliases[]
```

没有：

```text
normalized_name
```

的 UNIQUE。

所以未来两个并发 Settlement：

```text
Request A:
Statistics 不存在

Request B:
Statistics 也不存在
```

同时：

```text
INSERT Statistics UUID-A
INSERT Statistics UUID-B
```

数据库都可能成功。

最后一个用户拥有两个：

```text
Statistics
Statistics
```

这会再次破坏 repetition 的 `skillId` 身份。

### 建议 Stage2 RPC 前确定

MVP 简单方案：

```sql
normalized_name text
```

然后：

```sql
unique(user_id, normalized_name)
```

更长期的方案：

```text
skills
+
skill_aliases
```

其中：

```sql
unique(user_id, normalized_alias)
```

这样才能真正支持：

```text
Statistics
统计学
统计
Statistics Analysis
```

收敛到同一 Skill ID。
