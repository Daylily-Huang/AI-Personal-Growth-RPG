# P0：`0019_schema_integrity.sql` 当前很可能根本执行不了

这是这轮最重要的问题，而且不是设计争议，是 SQL 语法问题。

你当前写了多处：

```sql
alter table public.evidence_records
  add constraint if not exists
  evidence_records_evidence_level_check
  check (...);
```

以及：

```sql
alter table public.xp_transactions
  add constraint if not exists fk_...
```

以及：

```sql
alter table public.skills
  add constraint if not exists
  skills_user_normalized_unique
  unique (...);
```



问题在于 PostgreSQL 的 `ALTER TABLE ... ADD CONSTRAINT` 语法**没有 `IF NOT EXISTS` 这个位置**。官方 PostgreSQL 17 文档列出的形式是：

```text
ADD table_constraint [ NOT VALID ]
```

而 `IF NOT EXISTS` 支持的是 `ADD COLUMN` 等形式；`DROP CONSTRAINT` 支持 `IF EXISTS`，但 `ADD CONSTRAINT IF NOT EXISTS` 不是合法语法。

所以现在：

```text
0001
...
0018
↓
0019
↓
syntax error
```

的概率不是“可能有点高”，而是这是当前代码中一个明确的 blocker。

这也恰好说明为什么我前一轮坚持要求：

> **必须真正执行一次空库 migration，而不能只做字符串测试。**

---

# 应该怎么改

有两种正常方案。

**方案 A，我更推荐：用 DO block 检查 constraint 是否存在。**

类似：

```sql
do $$
begin
  if not exists (
    select 1
    from pg_constraint
    where conname =
      'skills_user_normalized_unique'
  ) then
    alter table public.skills
      add constraint
      skills_user_normalized_unique
      unique (user_id, normalized_name);
  end if;
end $$;
```

FK 和 Evidence CHECK 同理。

**方案 B：如果 migration 只要求“顺序执行一次”，直接使用标准 `ADD CONSTRAINT`。**

因为 migration 系统本身应该记录：

```text
0019 已执行
```

通常没必要让每条 migration SQL 自己无限幂等。

对于 Supabase migration，我倾向 **B 更简单**；对于你特意想兼容“某些库已经部分手工执行”的情况，再用 A。

这不是刷 XP 那么严重，但与规则治理直接冲突。


但是 Activity 表里面不仅有普通用户内容，还有：


其中 `rules_version` 按我们的治理原则应该是：

> **Activity 创建时冻结。**

所以如果 authenticated 用户可以直接：

```sql
UPDATE activities
SET rules_version = 'whatever'
```

那“冻结版本”其实没有数据库级保证。

类似地，confirmed Activity 也可以通过 Data API 改：

```text

status
effective_minutes
```

从审计角度也不理想。

## 不建议马上把 Activity 完全只读

因为用户确实需要：

```text
创建 Activity
编辑尚未确认的 Activity
```

所以这里需要区分：

```text
Draft / unconfirmed mutable
Confirmed immutable
```

推荐 Stage2 做一个小的 DB invariant：

```text
confirmed Activity
→ raw_input / rules_version /
   effective_minutes / status
→ 普通用户不可直接修改
```

以及：

```text
rules_version
→ creation 后不可由普通 client 修改
```

实现方式可以是：

- trigger；
- controlled RPC；
- 或取消 general UPDATE，让服务端提供受控更新函数。

**不要只靠 UI 不显示编辑按钮。**

# P2：Skill normalized identity 的注释写过头了

`0019` 注释说当前 normalization 能防：

```text
"Statistics" / "统计学" / "统计"
```

产生重复 Skill。

实际上 SQL 只是：

```sql
lower(
  btrim(
    regexp_replace(name, '\s+', ' ')
  )
)
```

所以它只能收敛：

```text
Statistics
 statistics
STATISTICS
Statistics   ← 空白变化
```

它**不会**知道：

```text
Statistics
统计学
```

语义上相同。

这不是当前 bug，因为 semantic alias 本来就在未来 Skill Ontology 范围。

但注释应该改准确，否则未来 Coding Agent 很容易误以为已经实现了跨语言 alias resolution。

建议描述成：

> normalized_name prevents case/whitespace duplicates; semantic aliases are handled separately.
